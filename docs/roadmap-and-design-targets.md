# Punch-Out!! (Wii) — Recomp Roadmap & Design Targets

**Guiding principle: efficiency and reliability come first.** Every design choice is judged on whether it makes the game cheaper to run on low-end hardware and whether it fails loudly and predictably instead of silently misbehaving.

The requirements and scope are the same as GBTG-Qilincomp's (Grabbed by the Ghoulies), applied to the Wii the way BeatTheBeat-QilinComp applies them. Where the Wii differs from the Xbox, this document says how the same rule applies.

## Targets
- **Game:** *Punch-Out!!* (Next Level Games, 2009), Europe/Australia, disc `R7PP01`, **revision 1** (Redump: "Punch-Out!! (Europe, Australia) (En,Fr,De,Es,It) (Rev 1)"), recognised by the SHA-256 of `main.dol`. Other regions and revisions are other binaries and out of scope for now.
- **Platforms:** 64-bit Windows, Linux and macOS (Intel and Apple Silicon), on x86-64 or ARM64, with Vulkan. See *Hardware scope* below.
- **Language:** **C++23** throughout (recompiler, generated code and runtime). Minimum compilers: GCC 14, Clang 19, Xcode 16, Visual Studio 2022 17.10.
- **Graphics API:** **Vulkan 1.3, and only Vulkan.** We require the 1.3 core API, and only the optional features and limits that Mesa's v3dv driver on a Pi 4 provides, so one render path works everywhere (MoltenVK on macOS). See *Vulkan baseline* below.
- **Reference:** Dolphin running the original game is ground truth for behaviour, visuals and audio. There is no decompilation of this game and no public symbol map (`prior-art.md`), so names come from our own analysis (see *Symbol naming*).
- **Timing accuracy:** Punch-Out!! is a reaction game: every opponent telegraphs an attack with a visual and audio cue, and the player has a window of a few frames to dodge or counter. So timing is behaviour. Cue-to-attack timing, dodge and counter windows, and input-to-screen and input-to-audio latency are measured against Dolphin, and on the low-end reference hardware, at every milestone from step 5 on.
- **Enhancement example target:** 3440×1440 (21:9) at 144 Hz.

## Architecture
- **Game code:** static recompilation, PowerPC (Broadway) → **generated C++**, compiled AOT by clang/GCC/MSVC for each target. No interpreter, no JIT, and no emulator underneath. Hand-written C++ replaces lifted functions over time (hot paths, bugs, enhancement hooks) through a function override table.
- **Decoder:** **our own, table-driven** (`recomp/src/decoder.*`, from BeatTheBeat-QilinComp v0.2.0). Broadway's encoding is fixed-width and small (222 instructions with the paired singles), and no proven, permissively licensed Broadway decoder exists to vendor the way Ghoulies vendors Zydis. It is **verified word by word against GNU binutils' `broadway` disassembler**: over every word of the game's text sections, and over a sweep of the encoding space in CI. Reserved bits set and invalid forms decode as invalid.
- **Symbol naming:** no decomp or map exists for Punch-Out!!, so names are earned in analysis, cheapest first: (1) the SDK and the other linked libraries (Revolution SDK, MSL, the PowerPC EABI runtime, MetroTRK, the HOME Button Menu, Wwise) identified by their version strings, assert and error strings, and by aligning function size sequences against the libraries other Wii decomps name (the CC0 Rhythm Heaven Fever decomp is already vendored in BeatTheBeat-QilinComp, and links an SDK of the same family); (2) C++ class names from vtables and RTTI-style strings (the game's engine leaves `nl*`, `Sl*`, `FE*` and `AK::` names in `.rodata`); (3) everything else stays `fn_<address>`.
- **Register model:** guest registers held in host locals inside each lifted function and synced to a context struct only at call/indirect boundaries: 32 GPRs, 32 FPRs as paired-single pairs (`ps0`, `ps1`), CR fields, XER, LR, CTR. No global or thread-local register variables (that model blocks host register allocation).
- **Calling conventions:** the game and its libraries are CodeWarrior-compiled PowerPC EABI code (arguments in `r3`–`r10` and `f1`–`f8`, small-data bases in `r2`/`r13`). Lifted code still keeps full register state across calls; ABI recovery only where hand-written C++ replaces a function.
- **Fail loudly:** an undecodable or unsupported instruction is a build error, never a comment; an unknown indirect-call target at runtime traps with its address logged. Encodings a retail compiler never emits (reserved bits set, invalid forms) count as undecodable.
- **Control flow:** recursive-descent CFG with resolved switch tables (CodeWarrior's `lis`/`addi`/`lwzx`/`mtctr`/`bctr` pattern). Indirect calls (`bctrl` through function pointers and vtables) dispatch through a generated sorted function table; an unknown target traps with the address logged (never silently continues), and the address is added as a seed.
- **Endianness:** the guest is big-endian and every host is little-endian. Guest memory keeps the guest's byte order, so file data and bulk copies need no conversion; each lifted load and store swaps bytes, a single instruction on x86-64 (`movbe`/`bswap`) and ARM64 (`rev`).
- **Lifter efficiency:** CR and XER elimination through dataflow analysis (compute only the CR bits a branch or `mfcr` reads; summary overflow only where read). Floating point is native `double`/`float`, bit-exact: Broadway's `fmadd` family is fused (one rounding), so it becomes `std::fma`, and `-ffp-contract=off` keeps the host compiler from fusing anything else. Broadway's quirks (the 25-bit rounding of `frC` in single-precision and paired-single multiplies, the `fres`/`frsqrte`/`ps_res`/`ps_rsqrte` estimate tables, non-IEEE mode) are reproduced and proven by the differential test. GQR-quantised `psq_l`/`psq_st` become inline conversions. Flat memory (4 GB host reservation, `base + addr`, no bounds checks).
- **Memory map and mirrors:** the game sees MEM1 (24 MB at `0x80000000`) and MEM2 (64 MB at `0x90000000`), each with an uncached mirror (`0xC0000000`, `0xD0000000`), plus hardware registers at `0xCC000000`/`0xCD000000`. Because we replace the hardware-facing SDK libraries, during bring-up any access to a mirror or a hardware register traps, so we learn exactly which ones lifted code uses. Only those get aliased mappings (file mapping / memfd) or native handling. Known case: the GX write-gather pipe at `0xCC008000` (see *Graphics*).
- **Exceptions:** decided in analysis (v0.3.0, `runtime-analysis.md`): no thrower or unwinder is linked and the game, engine and Wwise have no exception tables, so nothing can throw. The tables are dead data and the runtime has no unwinding.
- **System software (the Wii's "kernel and XDK"):** there is no kernel on the PowerPC side. The Revolution SDK (this build: `0x4199_60831`, libraries built March–October 2008) is linked into `main.dol` and drives the hardware registers and IOS (the ARM co-processor that owns storage, USB and Bluetooth) directly. Its hardware-facing libraries are **replaced natively at their API**, not recompiled: OS (threads, mutexes, message queues, alarms, interrupts, caches, time), DVD (files over the extracted disc), VI (presentation), GX (Vulkan), AI/AX/DSP (native mixer), WPAD with the Bluetooth stack and USB under it (Wii Remote input), SI and EXI, NAND/IPC/ES/FS (saves in a host folder), SC (console settings). Libraries whose exact behaviour matters more than native speed are **lifted** with the game: the C and C++ runtime (MSL, PowerPC EABI runtime), the pure-software SDK libraries (MTX/VEC maths, MEM heaps, ARC, TPL, AXFX, KPAD's and WBC's processing of Wii Remote and Balance Board data), THP's decoder, RFL (Mii data, over the replaced NAND), the HOME Button Menu (HBM and its private NW4R copy, `nw4hbm`), Audiokinetic **Wwise** (the game's sound engine: banks, events, streaming and its own mixing, on top of AX) and Next Level Games' engine (the `nl*` libraries: resources, scenes, animation, its scripting language). `code-analysis.md` has the boundary library by library, with each one's range (v0.2.0); it can still move as the runtime is written, as Ghoulies moved the CRT and XAPI to the lifted side in v0.11.0 and v0.12.0. Hot, simple lifted functions can still get native versions, each checked against the lifted original.
- **Graphics:** GX API-level translation to Vulkan, not Hollywood GPU emulation. The game draws with Next Level Games' own renderer straight on GX (no NW4R g3d; the cel-shaded look comes from its ramp, rim-light and outline techniques). **Plus a GX command-stream decoder** for what reaches the write-gather pipe directly: CodeWarrior inlines GX's vertex macros (`GXPosition3f32` …) into game code as stores to `0xCC008000`, and display lists (`GXCallDisplayList`) are raw command streams. Both become draws with the current vertex format; unknown commands assert. TEV stage and blend configurations are collected in analysis and converted to SPIR-V offline; prebuilt pipeline cache (no runtime compile stutter). Embedded-framebuffer copies (render to texture) are handled explicitly. THP movies decode on the CPU (lifted) and upload as textures.
- **Audio/Input:** AX voices (ADPCM and PCM, mixed by the DSP on the Wii) → native mixer on SDL3 or miniaudio; the DSP microcode is not emulated. Wwise sits above AX, lifted, so its mixing and streaming behave as on the Wii; the Wii Remote speaker output it drives (`CAkWiimoteMgr`) goes to the host mixer as an extra source or is dropped by setting. Output latency is a first-class target. Input: **buttons only, no motion controls** (a decision for this port). The game is driven through its sideways Wii Remote scheme (cross pad, 1, 2, A, +, −, HOME), which maps one to one onto a modern pad through SDL3: D-pad or left stick → cross pad, A/B → 2/1 (right and left punch), Y or X → A (Star Punch), Start/View → +/−, Guide → HOME; keyboard too, all remappable in the settings file. The replacement WPAD reports a sideways Wii Remote with no Nunchuk and no Balance Board, so the game's motion scheme and Balance Board dodging are never offered. KPAD and WBC stay lifted, since the game calls them either way.
- **Assets:** Next Level Games' resource files (`.data` with `.dict` and `.debug` companions, 1,194 of each), Wwise banks (`.bnk`) and streamed audio (`.wav`), THP movies, TPL textures and the HOME Button Menu's U8 archives (`.arc`) are read by the lifted code over the native DVD layer. Nothing is converted offline.
- **Threads:** audio mixing and Vulkan submission off the game thread. Guest OS threads run with the Wii's single-core, priority-based semantics (host threads under one run lock, or fibers); the choice is recorded when the scheduler is written.
- **Portability rules:** no inline asm or host intrinsics in the runtime; ARM64 Linux builds from day one.

## Hardware scope
**Supported: 64-bit hosts with a Vulkan 1.3 driver.** In practice that means:
- **Windows and Linux** on x86-64 or ARM64 with a Vulkan-capable GPU and driver;
- **macOS on Intel and Apple Silicon Macs**, through MoltenVK (Vulkan on top of Metal): any 64-bit Mac with a Metal GPU running macOS 10.15 (Catalina) or later: officially the 2012 and later Intel models, and every Apple Silicon Mac. MoltenVK has Vulkan 1.3 from v1.3.0, and its releases up to v1.4.1 still run on 10.15 (v1.4.2 raised the floor to 12), so Macs on 10.15–11 get one of those. The runtime (what players run) is built for macOS 10.15, and CI builds both architectures. It doesn't use `std::format`, which Apple's libc++ only has from macOS 13.3. The developer tools (`qilin`, the tests) use `std::format` and need macOS 13.3;
- **ARM boards** with Vulkan 1.3 drivers, e.g. Raspberry Pi 4 and newer (Mesa v3dv, Mesa 24.3 or later).

**Out of scope:** anything without Vulkan 1.3 (or, on Apple, a Vulkan translation layer that provides it), 32-bit hosts, and phones and tablets (iOS, iPadOS, Android). That rules out the Raspberry Pi 1–3 and Zero (OpenGL ES 2 only), the first Intel Macs (32-bit Core Duo, 2006), and Macs without a Metal GPU or that can't run macOS 10.15. Because of this there is one renderer (Vulkan) and one memory model: the Wii's 32-bit address space mapped flat into a 64-bit host's address space, with no windowing cost on memory accesses.

### Vulkan baseline: 1.3
The renderer targets **Vulkan 1.3** as its minimum API version, chosen for how widely it's supported:
- **Raspberry Pi 4 and 5:** Mesa's v3dv driver is Vulkan 1.3 conformant from Mesa 24.3.
- **macOS:** MoltenVK supports Vulkan 1.3 from v1.3.0, on Intel and Apple GPUs alike. Older Intel GPUs may lack some of the v3dv feature set; the start-up check names what's missing.
- **Windows and Linux:** current desktop GPU drivers (AMD, Intel, NVIDIA, Mesa) all ship 1.3.

1.3 makes several things core that would otherwise be extensions to probe for, and the renderer is designed around them:
- **Dynamic rendering:** no render pass or framebuffer objects. That suits GX's embedded framebuffer and its copies to textures.
- **Synchronization2:** simpler, less error-prone barriers.
- **Extended dynamic state:** cull mode, depth test and write, compare op, topology and stencil can be set per draw. That cuts down how many pipelines GX's state needs, which matters for the prebuilt pipeline cache.
- **Timeline semaphores** (core since 1.2): CPU–GPU pacing for frame timing.
- **Others:** `maintenance4`, inline uniform blocks, and pipeline creation cache control.

1.3 core is the floor, but optional features and device limits aren't: v3dv is the reference for those. The renderer checks the features it uses at startup and fails with a clear message if one is missing, rather than taking a fallback path. Nothing beyond 1.3 core and the v3dv feature set is used without a decision recorded here. Vulkan 1.4 is out of scope for the baseline.

**Low-end reference:** a Raspberry Pi 4–class board is our reference for typical low-end hardware. It's what we measure efficiency and reaction timing against and test on. It is not a floor: anything with Vulkan 1.3 that's slower is fair game if the efficiency work gets us there. The Vulkan feature set we use is kept small (1.3 core, plus what v3dv on a Pi 4 supports) so the one render path runs on all of it.

## Settings, not platform branches
All enhancements live behind a settings file with presets, e.g.:
- *Low-end:* 1× resolution, no AF, no MSAA, original aspect and frame rate.
- *Desktop:* scaled resolution, 16× AF, MSAA, widescreen, high refresh rate.

## Roadmap
1. **Analysis:** 🔨 in progress (`dol-analysis.md`, `recompiler-core.md`). ✅ the recompiler core so far brought over from BeatTheBeat-QilinComp (DOL loader, Broadway decoder, CFG, coverage, CI on six configurations); ✅ on the PAL `main.dol` (v0.1.0): build hash recorded, the decoder cross-check over every text word (0 unexplained), function discovery and CFG (13,487 functions, all 187 jump tables proven, every unreached word identified, none of it code we lift). ✅ every library found and its range fixed without a decomp, and the boundary decided, with every privileged instruction and every unknown word outside the lifted code (v0.2.0, `code-analysis.md`). ✅ the hardware-access profile, the exception tables and the frame timing model (v0.3.0, `runtime-analysis.md`): lifted code touches no register or mirror but writes the GX FIFO directly; nothing can throw; one frame per retrace with a time-step-driven simulation. Left for the runtime: whether the main loop's time step is fixed or measured, and the audio timing (Wwise's frame size against AX's 3 ms tick).
2. **Recompiler core (C++23):** ✅ CFG + data-as-code validation, every word of the code accounted for, jump tables with proven sizes (v0.1.0); ✅ lifter slice 1, integer with CR/XER, calls, branches and the function table, 80.9% of the functions lifted and all of the generated code compiling and linking (v0.4.0); ✅ slice 2, floating point, bit-exact as Dolphin's hardware tests record Broadway (NI mode, NaN rules, single rounding, 25-bit frC, the estimate tables), 94.8% of the functions (v0.5.0); ✅ slice 3, paired singles with GQR quantisation, 99.3% of the functions, every one in the libraries we lift (v0.6.0); a differential test against a reference executor: ✅ for slice 1, our own reference interpreter written from the manual separately from the lifter (v0.4.0); for floating point and paired singles, the same reference model extended from the 750CL manual and checked against Dolphin's results; then whole call trees, under UBSan too.
3. **Runtime skeleton:** 🔨 (v0.7.0, `runtime.md`) the `punchout` executable, built from the player's `main.dol`, loads the DOL into MEM1, sets up MEM2 and the boot information the loader leaves in low memory (memory sizes, arena bounds, bus and CPU clocks, console type), and runs start-up as the SDK runs it; a replacement registry that stops on anything unregistered, naming it and its caller; the OS, DVD and NAND replacements.
4. **Boot to first frame:** GX on Vulkan, the first copy to the external framebuffer presented.
5. **Playable at original spec:** original resolution, aspect and frame rate; matches Dolphin, reaction timing included; tested on low-end reference hardware at every milestone.
6. **Resolution / AF / MSAA:** scaled embedded framebuffer, copies to textures at the scaled resolution where that's safe, layout half-pixel fixups.
7. **Widescreen 16:9 → 21:9:** Hor+ projection, layout panes re-anchored, pillarboxing where a scene can't widen.
8. **High refresh rate:** investigate the game's tick model first. A fighting game's logic usually runs on a fixed 60 Hz tick (cue and dodge windows are counted in ticks), which decides whether higher refresh rates need interpolation or just pacing.
9. **Extras:** texture replacement packs (hash on upload), etc.
